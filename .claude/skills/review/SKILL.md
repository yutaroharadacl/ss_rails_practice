# コードレビュー Skill

このSkillは、このRails学習リポジトリで作業中の変更をレビューするための手順です。`CLAUDE.md` のAI振る舞い方針（チューター寄り）とコーディング規約に従って進めてください。

## 対象範囲

1. `git status` で未追跡ファイル・変更ファイルを確認する。
2. `git diff` / `git diff --staged` で作業中の変更を確認する。
3. 作業ツリーがclean（未コミットの変更なし）な場合は、`git branch --show-current` で現在のブランチを確認し、`git diff main...HEAD`（または `git diff origin/main...HEAD`）で「mainから分岐して以降の変更」をレビュー対象にする。
4. レビュー対象の変更が見つからない場合は、その旨を伝えて対象ファイル・ブランチを学習者に確認する。

このSkillはPR番号を指定したレビューは対象外。特定のPRをレビューしたい場合は組み込みの `code-review` Skillを使う。

## モードの選択

- **高精度モード（デフォルト）**：「レビューして」「コードレビューして」など、特に指定がない場合はこちらを使う。手順は下記「高精度モード（code-review相当）」を参照。
- **簡易モード**：学習者が「軽く」「さっと」「簡単に」「ざっと見て」のように明示的に求めた場合のみ使う。下記「手順」の通り、自分で対象範囲を読んで指摘をまとめる、軽量なチューター向けレビュー。

## 手順（簡易モード）

学習者が「軽く」「さっと」「簡単に」のように明示的に求めた場合のみ、この手順を使う。

1. **変更の目的を理解する**
   - diffの内容から、何を実現しようとしている変更かを把握する。
   - 目的が読み取れない場合は、コードを推測で評価する前に学習者に「これは何をする変更か」を簡単に聞く。

2. **レビュー観点（この順で見る）**
   - **正しさ**: 意図通りに動くか。バグ・考慮漏れ（nilチェック、境界値、N+1など）がないか。
   - **Railsの慣習**: REST的なルーティング・命名、strong parameters、`app/controllers/api/base_controller.rb` のような既存の共通基底の使い方、named scopeやコールバックの適切さなど。
   - **リポジトリ規約**: `.rubocop.yml`（`TargetRubyVersion: 2.7`, `NewCops: enable`）に沿っているか、既存の構成パターン（例: `api/v1`, `api/v2` の名前空間分け）を踏襲しているか、過剰な抽象化をしていないか（学習用リポジトリなのでシンプルさを優先）。
   - **テスト**: 新機能・修正に対応するRSpec（`spec/requests/` など）があるか、そのspecが実際に意図した振る舞いを保証しているか。

3. **機械的チェックの実行**
   - `bundle exec rubocop`（対象ファイルのみでも可）を実行し、結果をレビューに含める。
   - `bundle exec rspec`（関連するspecディレクトリ指定でよい）を実行し、失敗があれば内容を共有する。
   - セキュリティに関わる変更（認証・入力値の扱いなど）が含まれる場合は `bundle exec brakeman` の実行も検討する。Ruby 2.7 / Rails 6.0のEOLに起因する `Unmaintained Dependency` 警告2件は既知のため指摘不要（`CLAUDE.md` 既知の注意点を参照）。

4. **指摘の伝え方**
   - 各指摘は「箇所（`ファイル:行`）」「何が問題か」「なぜそうすべきか（Railsの慣習やこのリポジトリの規約に紐づけて）」の3点セットで伝える。
   - 優先度を明示する（動作上の問題 > 規約・慣習からの逸脱 > 好みレベルのスタイル）。
   - **コードはこのSkill経由では書き換えない。** 指摘と理由の提示にとどめ、直すかどうか・どう直すかは学習者に委ねる。
   - 学習者が「直し方も見せて」「修正パッチも見たい」と明確に求めた場合は、該当箇所に絞った修正案（diff）を提示してよい。その場合も、実際にファイルを編集するかどうかは別途学習者に確認してから行う。
   - 良かった点（意図が明確、テストがある、既存パターンに沿っている等）があれば最低1つは伝える。

## 高精度モード（code-review相当、デフォルト）

「レビューして」など特に指定がなければ、以下の手順で進める。対象範囲の特定方法は上記「対象範囲」と同じ（`git status` / `git diff` / `git diff main...HEAD`）。「指摘の伝え方」（上記4番）の3点セット・優先度・書き換えない方針は、このモードでも`ReportFindings`の各フィールドを通じて満たす。

### フェーズ0：diffの収集

対象のdiffを1つのテキストとして確定させる（コミット済み・未コミット両方が対象になりうる点に注意。作業ツリーが汚れている場合は両方合わせてレビュー範囲にする）。

### フェーズ1：候補出し（8観点、それぞれAgentツールで最大6件）

以下の8つの観点を、それぞれ独立したAgentに並列で投げる（1メッセージ内で複数回`Agent`ツールを呼び出す、または依存がなければ順次バックグラウンド実行でよい）。各Agentには対象diffと関連ファイルを渡し、`file`/`line`/`summary`/`failure_scenario`の形式で最大6件の候補を返させる。

- **A. 行単位の正しさスキャン**：diffの各行を読み、境界値・nil・タイポ・条件の反転・変数の取り違えなどを探す。変更されたメソッド・アクションの周辺（diffに現れない既存コード）も読む。
- **B. 削除された挙動の監査**：diffで削除・置換された行それぞれについて、それが守っていた不変条件が新しいコードでも守られているか確認する。
- **C. クロスファイル追跡**：変更されたメソッド・ルート・パーシャル・ヘルパーの呼び出し元・呼び出し先を`grep`で辿り、前提条件やシグネチャの変化が壊れていないか確認する。
- **Reuse（再利用）**：このリポジトリに既にある似た仕組み（ヘルパー、パーシャル、SCSS、他コントローラのパターンなど）を再実装していないか。
- **Simplification（簡素化）**：不要な複雑さ・コピペ・デッドコードがないか。
- **Efficiency（効率）**：無駄なDBクエリ（N+1）・同じ計算の繰り返しがないか。
- **Altitude（深さ）**：症状に対する対症療法になっていないか、より根本的な直し方がないか。
- **Conventions（`CLAUDE.md`）**：リポジトリの`CLAUDE.md`（および該当ディレクトリ配下の`CLAUDE.md`があれば）を読み、明文化されたルールに違反している箇所だけを指摘する。ルール文を引用できないものは対象外。

正しさ（A/B/C）の指摘は、cleanup系（Reuse/Simplification/Efficiency/Altitude/Conventions）の指摘より常に優先度が高い。

### フェーズ2：検証（1票、再現性重視）

同じ欠陥・同じ箇所の重複候補はまとめる。残った候補それぞれについて、別のAgentに「diff・該当ファイル・候補の内容」を渡し、`CONFIRMED` / `PLAUSIBLE` / `REFUTED` のいずれか1つを判定させる。

- 競合状態、nilになりうる稀なパス、境界値、falsy-zeroの見落としなどは、実際にあり得る状態であれば`PLAUSIBLE`として残す（疑わしいというだけで却下しない）。
- `REFUTED`にできるのは、コードから機械的に反証できる場合のみ（実際に該当行を引用して事実と違うと示せる、型・定数から見て不可能と示せる、diff内で既に対処されている、見た目だけの好みで実害がない）。
- `CONFIRMED`と`PLAUSIBLE`は残し、`REFUTED`は落とす。

### 出力

`ReportFindings`ツールを1回呼び出して報告する（最大10件、重大度順、`file`/`line`/`summary`/`short_summary`/`failure_scenario`/`category`/`verdict`）。このモードでは指摘を会話文で重ねて書かず、ツール呼び出しを報告とする。ただし「注意点」（コードを勝手に書き換えない、直すかどうかは学習者に委ねる）は高精度モードでも変わらず適用する——`ReportFindings`は指摘の提示であって、修正の実行ではない。

## 注意点

- 動くコードを問答無用で書き換えない（`CLAUDE.md` 方針）。指摘は提案として提示する。
- レビュー対象外の無関係なリファクタ提案（過剰な抽象化の提案含む）はしない。
- このSkill自体はコミットやPR作成は行わない。レビュー後にPRを作る場合は `create-pr` Skillに引き継ぐ。
